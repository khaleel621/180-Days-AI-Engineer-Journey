### Python: OOP — Encapsulation and Access Modifiers

Implemented and tested `01-python-fundamentals/day17-encapsulation.py`:

**Concepts learned:**
- Encapsulation: bundling data (attributes) and the operations on that data (methods) into one class, and hiding the internal state.
- Public attributes: written as normal names (e.g. `self.account_holder_name`); anyone can read or write them from outside the class.
- Protected attributes: single leading underscore (e.g. `self._account_number`); a convention meaning "internal use", not a block.
- Private attributes: double leading underscore (e.g. `self.__balance`); Python applies name mangling (`_BankAccount__balance`), so direct access like `account.__balance` raises `AttributeError`.
- Getters and setters: `get_balance()` reads the private balance; `set_account_holder_name()` validates and changes the name.
- Input validation with `ValueError`: deposit/withdrawal amounts must be real numbers (bools rejected) and greater than zero; a withdrawal cannot exceed the balance.

**Exercises implemented:**
1. `BankAccount(account_holder_name, account_number, initial_balance=0)`
   - Public: `account_holder_name`
   - Protected: `_account_number`
   - Private: `__balance`
   - `deposit(amount)`, `withdraw(amount)`, `get_balance()`
   - `get_account_holder_name()` / `set_account_holder_name()` getter and setter
   - `get_account_number()` for the protected attribute
2. Demo in `main()` showing public access, validated setter, deposit/withdraw, invalid-amount rejection, insufficient funds, private-attribute blocking, name mangling, protected access, and object independence.

**Error-handling behaviour (chosen and documented):**
- All invalid input raises `ValueError` with a clear message.
- Deposit and withdrawal amounts must be numbers (bool rejected) and greater than zero.
- Withdrawal above the balance raises `ValueError` and leaves the balance unchanged.
- Account holder name and account number must be non-empty strings.

### DSA: Largest Rectangle in Histogram (Monotonic Stack)

Implemented `largest_rectangle(heights)` in `02-data-structures-algorithms/stacks/day17-largest-rectangle.py`:

**Concepts learned:**
- Largest Rectangle in Histogram: a rectangle spanning several bars is limited by the shortest bar in that span; area = height × width.
- Monotonic increasing stack of indices: the stack stores indices whose heights increase from bottom to top.
- Left-to-right traversal of the input, plus one sentinel bar of height 0 at the end to flush the stack.
- When a shorter bar arrives, it is the right boundary for all taller bars waiting on the stack; each is popped and measured.
- Width of a popped bar = current index - (new stack top + 1), or the full current index if the stack is empty.
- The original input list is not modified.
- Each index is pushed once and popped at most once: time complexity O(n), space complexity O(n).

**Examples verified:**
- `[2, 1, 5, 6, 2, 3] -> 10`
- `[] -> 0`
- `[5] -> 5`
- `[2, 2, 2] -> 6`
- `[1, 2, 3, 4] -> 6`
- `[4, 3, 2, 1] -> 6`
- `[2, 1, 2] -> 3`
- `[6, 2, 5, 4, 5, 1, 6] -> 12`

**Tests:** `test_day17_largest_rectangle.py` - all 9 tests passed, covering all required examples, equal heights, increasing heights, decreasing heights, mixed heights, and input immutability.
